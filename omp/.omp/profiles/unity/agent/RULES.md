# Profile defaults

- **Caveman is the default chat style in this profile.** At the start of a new session, read `skill://caveman` and follow it for chat responses. If the user says "stop caveman" or "normal mode", leave it off for the rest of that session until explicitly re-enabled. `/skill:caveman` enables it again. Do not apply this style to code, comments, documentation, specifications, or tickets; preserve technical content and use full sentences for warnings and questions.
- **Ponytail runs through the profile-local official extension.** Its default is `full`; `/ponytail lite|full|ultra|off` changes the current session. Saying "normal mode" also turns Ponytail off; use "stop caveman" to disable only the chat style. Simplicity and brevity never override the correctness, safety, architecture, or verification requirements below.
- **Hypa runs through the profile-local `@hypabolic/pi-hypa` extension in additive mode.** Keep using omp's built-in tools; eligible bash commands are automatically rewritten through the bundled Hypa binary. `/hypa` shows diagnostics. Configuration lives in this profile's `agent/hypa-pi.json`, selected by `agent/.env`; non-interactive confirmations are denied and MCP proxy discovery is disabled. Do not run `hypa init` or install global integrations as part of using this plugin.
- **Always use the `ask` tool for clarification, design decisions, and grilling questions.** Give each question exactly three distinct, meaningful options and mark one as recommended with the tool's `recommended` field. Explain the tradeoffs briefly, batch related independent questions, and wait for prerequisite answers before asking dependent questions. Do not replace the tool with a plain-chat question list. Do not supply an "Other" option; the UI provides custom input. Look up tool- or repository-provided facts rather than asking the user for them.

# Unity 6.6 / ECS-DOTS

These rules apply to Unity/game-development work in this profile; do not impose Unity architecture on unrelated repositories.

- **Target Unity 6.6 (6000.6).** Inspect the exact project Editor version, resolved DOTS/package versions, assemblies, rendering pipeline, scripting backend/API compatibility, and target platform before choosing APIs. Report version mismatches; never silently upgrade them. The desktop .NET SDK and older skill examples do not establish Unity compatibility.
- **Preserve the project architecture and runtime boundaries.** In this ECS/DOTS project, keep gameplay/simulation in ECS; use MonoBehaviours for authoring, UI/presentation, or explicit managed bridges, not a replacement gameplay architecture. Reuse intentional ISystem/SystemBase, baking, world, and system-group conventions. Do not migrate between ECS, GameObject, or hybrid architectures without explicit user approval. This does not freeze entity archetypes, component layouts, or legitimate system changes.
- **Read unity-dots-runtime first for DOTS work**, then use unity-ecs-patterns where relevant. Read supporting skills only for their actual boundary: unity-input-system, unity-csharp-scripting, and unity-scriptableobjects do not override the ECS simulation design. Resolve version-specific APIs against installed packages; do not mechanically follow upstream claims such as "Burst compile everything".
- **Keep safety and ownership explicit.** Propagate job dependencies, respect ECB playback and reference invalidation, and dispose only owned native resources after their readers complete. Preserve scene/world and managed-object lifetime; unsubscribe/cancel/reset owned work at teardown. Do not hide races by suppressing safety checks. UnityEngine APIs stay on the main thread unless the specific API documents otherwise.
- **Preserve the physics stack.** Distinguish Unity.Physics/Havok DOTS physics from classic PhysX; use the project's existing stack and matching scheduling, query, and event APIs.
- **Protect assets and keep hot paths lean.** Preserve .meta/GUID identity and prefer connected Editor APIs for scene/prefab/asset changes. Avoid unnecessary allocations, copies, lookups, and sync points in frame/physics loops. Back performance claims with comparable profiler evidence, not architecture labels.
- **Verify actual Unity behaviour.** Compile/import through the target Editor and exercise changed behaviour in the relevant world/scene, confirming advancing ticks and observable results. Use installed Unity Test Framework/NUnit EditMode/PlayMode APIs and the project's test assemblies; dotnet test is only for genuinely standalone SDK projects. Tests need meaningful state/behaviour assertions and deterministic cleanup. State runtime limitations explicitly.
- **No silent installation or upgrades.** Approval for this profile setup is not blanket approval to install/update Editors, CLI tools, Unity packages, plugins, MCP servers, or telemetry. Keep skill changes in this profile's configured stores; never use global skills installs or mirror them into other agents' directories.
- **Use the native specialists when delegating genuine slices.** unity-dots-gameplay owns implementation; unity-dots-reviewer performs read-only, evidence-backed review. One parent/integration owner performs the final smoke/build/test phase; delegated slices do not run mid-flight checks. Never claim unobserved verification.
